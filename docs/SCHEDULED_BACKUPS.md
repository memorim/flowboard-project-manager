# Резервные копии SQLite по расписанию

При запуске Node API планировщик создаёт проверенную копию существующей базы, затем повторяет её по расписанию. Используется существующий SQLite online backup, проверка целостности и внешних ключей. Статус хранится атомарно в `status.json`, поэтому перезапуск процесса учитывает время последней успешной копии.

| Настройка | По умолчанию |
|---|---|
| `BACKUP_ENABLED` | `true` |
| `BACKUP_INTERVAL_HOURS` | `24` |
| `BACKUP_RETENTION_DAYS` | `7` |
| `BACKUP_DIR` | `data/backups` |
| `BACKUP_ALERT_WEBHOOK_URL` / `BACKUP_ALERT_TOKEN` | пусто |

Просмотр статуса: `pnpm backup:status`. Разовая копия и восстановление описаны в [предыдущем руководстве](ROUND3.md).

Очистка касается только файлов `auto-*.sqlite` этого планировщика и выполняется после новой успешной копии. Ручные файлы и символьные ссылки не удаляются. При сбое — повтор через пять минут, событие `backup_alert` и код обращения в журнале. Настроенный HTTPS webhook получает одно уведомление до восстановления; без адреса используются журнал и файл статуса. Текст ошибок, содержимое базы и секреты в уведомление не попадают.

Планировщик работает, пока запущен сервер. Для нескольких процессов нужен один выделенный владелец расписания; текущая блокировка не распределённая. Копия рядом с базой не защищает от потери диска — архив нужно переносить в независимое хранилище. Хостинговая D1 имеет другой жизненный цикл: эти настройки к ней не применяются.
