# Размещение, обновление и перенос

## Один комплект исходников

`pnpm build` создаёт frontend, а Express раздаёт `dist` и `/api` с одного origin. Dockerfile собирает тот же вариант. Для полной версии не нужен D1 или отдельная копия интерфейса. Старый `hosting/` остаётся выдержкой прежнего размещения, а не активным target этого релиза.

Локальный `compose.yaml` поднимает приложение, PostgreSQL 16 и Mailpit. Он не является production-конфигурацией: bind только loopback, HTTP, Mailpit вместо внешней почты. `pnpm setup:local` создаёт случайные секреты, не перезаписывая существующий `.env`.

## Публичный сервер

- Соберите образ из проверенного commit SHA; передайте `APP_REVISION=<тот же SHA>`.
- `NODE_ENV=production`, `FLOW_AUTH_MODE=session`, HTTPS `FLOW_PUBLIC_ORIGIN`; корректная TLS-терминация перед приложением. Порт backend должен быть доступен только доверенному прокси.
- Передайте DATABASE_URL и FLOW_APP_KEY из secret storage. Сохраните key между релизами. Для внешней PostgreSQL настройте проверяемый TLS согласно провайдеру; не отключайте проверку сертификата.
- Несколько экземпляров приложения используют одну PostgreSQL и ту же схему/key. Не используйте сетевой том SQLite как замену PostgreSQL.
- Настройте SMTP и тестовый магазин по [инструкции интеграций](INTEGRATIONS.md). Рабочие email/платежи не включаются от одной публикации исходников.
- Если прокси меняет client IP, задайте точное число доверенных hops. Не разрешайте альтернативный более короткий публичный путь к backend.

Защита запросов распределяется через атомарные UPSERT в общей БД; квоты задаются FLOW_WRITES_PER_MINUTE, FLOW_WORKSPACE_QUOTA, FLOW_PROJECT_QUOTA, FLOW_INVITATION_QUOTA (1..10000). Core API допускает 600 запросов на IP в минуту. Для публичного сервера дополнительный общий ingress limit относится к конфигурации вашего прокси. План «Команда» повышает только квоту проектов.

## Обновление

1. Проверьте CI нужного SHA и сохраните прежний образ/настройки.
2. Остановите запись, сделайте резервную копию БД и FLOW_APP_KEY.
3. Проверьте восстановление копии в отдельную БД; запустите новый образ сначала там.
4. Новая SQLite-схема добавляется транзакционно. PostgreSQL запускает миграции под advisory lock и сверяет SHA-256 применённых файлов. Применённые миграции не редактируются.
5. Запустите приложение; проверьте `/api/health` и X-App-Revision, вход, приватную задачу, конфликт версии, письмо, SCIM и оплату в тестовом магазине.
6. Возобновите доступ после проверок. Откат изменения схемы выполняйте восстановлением копии в отдельный volume/DB; не пытайтесь угадать совместимость старого кода с новой схемой.

SIGTERM прекращает приём новых запросов, затем завершает очереди писем/платежей и закрывает БД. Lease позволяет другому процессу продолжить работу после аварийного завершения.

## PostgreSQL backup/restore

Используйте инструменты PostgreSQL той же основной версии. Пример для отдельной БД (DATABASE_URL — секрет оператора):

```bash
pg_dump --format=custom --file=flowboard-backup.dump "$DATABASE_URL"
# Восстанавливайте в новую пустую БД, не поверх работающей:
pg_restore --no-owner --dbname="$RESTORE_DATABASE_URL" flowboard-backup.dump
```

Файл dump содержит приватные данные и зашифрованные секреты; храните защищённо. Секрет FLOW_APP_KEY сохраняйте отдельно. Автоматическое расписание/внешнее хранение PostgreSQL backup настраивает оператор; встроенный backup scheduler относится только к SQLite. [SQLite backup](SCHEDULED_BACKUPS.md).

## SQLite → PostgreSQL

1. Обновите SQLite до этой версии, проверьте доступ и остановите приложение.
2. Создайте SQLite backup; исходный рабочий файл не используйте для экспериментов.
3. Создайте отдельную пустую PostgreSQL/schema; задайте DATABASE_URL и прежний FLOW_APP_KEY.
4. `pnpm db:import-sqlite path/to/offline-backup.db` читает backup read-only. Подготовка схемы, перенос в транзакции, хеш-сверка всех строк каждой таблицы, настройка ID; непустая целевая БД отклоняется. При ошибке переноса данные откатываются.
5. Сравните результат, вход и права. Только после этого переключите сервер на новую БД. Сохраните backup до завершения проверки.

Офлайн-импорт держит одну таблицу в памяти; для больших объёмов нужен streaming COPY. Не запускайте приложение одновременно с импортом. Рабочая SQLite не удаляется и не изменяется импортом.

## Граница проверенного

Этот цикл проверяет исходники, локальные PostgreSQL/SMTP и Docker. Он не публикует полный сервер поверх прежнего общего Sites-размещения: оно обслуживает также другой проект. Для переноса публичного адреса потребуется отдельный сервер и ваши внешние реквизиты. GitHub Pages продолжает работать как браузерная версия.
