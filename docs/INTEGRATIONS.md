# Подключение интеграций

Интеграции относятся к полному Node-серверу. Их настройки не добавляют секреты в frontend или GitHub Pages.

## Почта

Подойдёт SMTP вашего почтового провайдера: `SMTP_HOST`, `SMTP_PORT`, `SMTP_FROM`, при необходимости `SMTP_USER` и `SMTP_PASSWORD`. Порт 465 использует TLS сразу; на других внешних портах требуется STARTTLS. `FLOW_SMTP_ALLOW_PLAINTEXT=true` действует только вне production и нужен для контейнера Mailpit в локальном Compose.

Нужны постоянный `FLOW_APP_KEY` (32 случайных байта в base64) и доверенный `FLOW_PUBLIC_ORIGIN`. Письма шифруются в outbox. Worker выбирает до 10 сообщений за цикл, берёт lease на 120 секунд, допускает пять попыток с backoff; успешный payload очищается. Статусы сохраняются при перезапуске. После пяти неудач запись получает failed_at и хранится семь дней; исправив SMTP, пользователь может запросить новую ссылку. SMTP не гарантирует exactly-once: возможен повтор после сбоя между доставкой и коммитом. Message-ID стабилен.

### Бесплатная отправка через HTTPS на Render

Render Free [блокирует исходящие SMTP-порты 25, 465 и 587](https://render.com/docs/free). Можно выбрать `FLOW_MAIL_PROVIDER=brevo`: адаптер отправляет запрос на фиксированный HTTPS API, не следует перенаправлениям и ограничивает запрос 15 секундами. SMTP остаётся режимом по умолчанию для существующих установок.

У Brevo на дату проверки 07.11.2026 [Free включает 300 отправок в день](https://help.brevo.com/hc/en-us/articles/208589409-About-Brevo-s-pricing-plans). Создайте аккаунт, подтвердите отправителя и выполните требования сервиса к домену. В Render задайте `BREVO_API_KEY`, `BREVO_FROM_EMAIL` и при необходимости `BREVO_FROM_NAME`. Ключ хранится только в серверном окружении; в Git и переменные `VITE_*` его не добавляют. `FLOW_APP_KEY` и `FLOW_PUBLIC_ORIGIN` нужны и в этом режиме.

API использует [отправку транзакционных писем](https://developers.brevo.com/docs/send-a-transactional-email). Существующие шифрование, аренда, пять попыток и очистка payload сохранены. Только ответ 201 с `messageId` подтверждает приём сервисом; это ещё не доказательство доставки в ящик. Заголовок `X-Flowboard-Event` стабилен между попытками и помогает найти письмо, но не заявляет дедупликацию провайдером. После сбоя между приёмом и коммитом возможен повтор.

Перед включением регистрации проверьте на собственном адресе полный цикл: регистрация → получение письма → подтверждение → вход → восстановление → новая ссылка и вход с новым паролем. Нужны настоящий ключ и подтверждённый отправитель; тесты адаптера не заменяют эту проверку. Пока они не подключены, почтовой этап размещения остаётся незавершённым.

## SCIM 2.0

Владелец пространства открывает управление пространством → «Каталог сотрудников», подтверждает пароль и создаёт токен. Скопируйте его сразу: сервер хранит только SHA-256. Срок 90 дней; замена или отключение немедленно прекращает новые запросы старого токена.

Base URL: `https://your-flowboard.example/api/scim/v2`, авторизация `Authorization: Bearer <token>`, JSON `application/scim+json`. Доступ ограничен пространством, привязанным к токену. Роль новых участников выбирает владелец: editor или viewer.

Поддерживаются discovery endpoints, Users и Groups GET/POST/PUT/PATCH/DELETE, пагинация startIndex/count (до 100 на страницу), eq-фильтры userName/externalId/displayName, ETag/If-Match. Пример:

```http
POST /api/scim/v2/Users
Authorization: Bearer <token>
Content-Type: application/scim+json

{"schemas":["urn:ietf:params:scim:schemas:core:2.0:User"],"userName":"person@example.com","displayName":"Участник","active":true,"externalId":"employee-42"}
```

Для нового адреса создаётся неактивированный аккаунт и письмо установки пароля. Существующий аккаунт сохраняет пароль и другие пространства. Деактивация отзывает членство и назначения задач только в этом пространстве. Владелец и неуправляемые члены не захватываются каталогом. Профиль каталога не переписывает глобальное имя аккаунта.

`userName` неизменяемый. Группы плоские, только SCIM-пользователи этого пространства, до 1000 участников. Bulk и вложенные группы не поддерживаются. Это проверенное подмножество [RFC 7644](https://www.rfc-editor.org/rfc/rfc7644), а не заявленная сертификация конкретного IdP.

## ЮKassa

1. Создайте **тестовый** магазин, добавьте `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`, постоянный случайный `FLOW_YOOKASSA_WEBHOOK_TOKEN` (64 hex).
2. `FLOW_TEAM_PRICE_CENTS` задаёт цену в копейках. По умолчанию 99000 = 990 ₽. `FLOW_BILLING_ALLOW_LIVE=false` оставляет запрет на подтверждение реальных платежей.
3. В кабинете магазина настройте HTTPS callback `https://your-flowboard.example/api/billing/webhook?token=<secret>` для payment.succeeded/payment.canceled. Не включайте query string с секретом в логи внешнего прокси.
4. Владелец пространства может оплатить план «Команда»: квота проектов ×4 на 30 дней. Автопродления нет. После окончания записи сохраняются, создание сверх базовой квоты приостанавливается.

Сумма и workspace проверяются по сохранённой операции. Клиентский Idempotency-Key привязан к владельцу и пространству; API магазина получает стабильный UUID. Callback не является доказательством оплаты: сервер запрашивает платёж по merchant API и проверяет сумму, RUB, metadata, paid и test. Фоновый worker сверяет ожидающие операции и восстанавливает потерянный ответ с тем же UUID.

[ЮKassa хранит ключ идемпотентности 24 часа](https://yookassa.ru/developers/using-api/interaction-format). Неопределённый запрос без provider_id автоматически повторяется лишь в первые 23 часа. Более старую операцию оператор сверяет в кабинете; повторное списание под новым ключом не создаётся автоматически. Возвраты выполняются в кабинете, автоматической обработки возвратов и налоговых чеков в этом проекте нет. Перед реальными платежами оператор должен проверить необходимые настройки магазина и условия приёма оплаты.

Проверки используют управляемую заглушку merchant API и настоящий PostgreSQL. Они подтверждают логику приложения, но не заменяют транзакцию в тестовом магазине: нужны ваши реквизиты. [Тестовый режим ЮKassa](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing).
